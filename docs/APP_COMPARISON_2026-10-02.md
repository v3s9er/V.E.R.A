# 실제 설치 앱의 네 구성 비교

본문의 네 문항 비교는 **0.6.2 당시 기록**이다. 현재 설치된 0.6.3의
시간초과 복구 수정과 한 문항 재검사는 문서 마지막에 별도로 기록한다.

## 무엇을 비교했나

Windows에 설치된 Mr.Robot의 인증된 루프백 `chat.start`를 호출했다.
이는 채팅 화면과 같은 서버 진입점이며 별도로 생성한 AgentLoop나 직접 CLI에
문제를 넣은 결과가 아니다. Computer Use는 사용하지 않았다. 앱 자체가
선택한 내부 CLI 경로와 회의 경로가 실행했고 결과 대화를 저장했다.

같은 `gpt-6-sol`, `medium`, Daybreak 꺼짐, 작업공간 권한, `quality` 질문
예산으로 AIME 2022 I-01/I-06/II-01/II-06 네 문항을 비교한다. 각 문항과
구성은 새로운 프로젝트·대화를 사용하며, 앱 외부의 정답 캐시는 전달하지
않는다. 프롬프트는 네 구성에서 동일하다. 최종 줄 `Answer: N`의 정수와
참조 정답이 정확히 일치해야 통과한다. 요청당 180초, 구성당 한 번이며
재시도 결과로 실패를 덮어쓰지 않는다.

| 구성 | 앱 설정 |
| --- | --- |
| 단일 | 네이티브 Sol 6 한 세션 |
| 관계 메모리 | 단일 + 해당 프로젝트·대화에 한정된 주어/속성/값 사실 |
| 오케스트레이션 | 독립 Sol 6 풀이 둘을 병렬로 수집 → Sol 6 최종 검증 |
| 둘 다 | 같은 회의 구성 + 관계 메모리 |

메모리는 문제의 **주어진 조건만 구조화**한다. 정답·풀이·추가 힌트를
저장하지 않는다. 완전한 온톨로지 추론 엔진의 효과를 측정한 것은 아니다.
오케스트레이션도 고정된 2+1 구성으로, 마스터가 노드 수를 자유롭게 정하는
모든 전략의 성능을 대표하지 않는다.

문항 순서에 따른 구성 순서는 단일/메모리/둘 다/회의,
메모리/회의/단일/둘 다, 회의/둘 다/메모리/단일,
둘 다/단일/회의/메모리다. 각 구성이 각 실행 위치에 한 번씩 놓인다.

## 검증 중 발견한 결함

1. 0.6.1 네이티브 경로가 Daybreak 관련 프로토콜 필드를 보내면서 필요한
   기능 협상을 빠뜨렸다. 초기 6개 진단 실행은 중단했다.
2. MCP 페이징 도구가 모든 질문에 붙어 실행 모델 선택에 영향을 줄 수 있었다.
3. 다음 후보 빌드에서 `greatest`를 `test`로 인식했다. 마지막 문항의 두
   회의 구성은 의도와 달리 다른 실행 모델로 넘어가 HTTP 503으로 실패했다.
   이 16개 실행을 고정 Sol 6 정확도 점수로 사용하지 않는다.

문제 프롬프트나 정답에 맞춘 추론 튜닝 대신 일반적인 프로토콜 협상과
영어 단어 판별을 수정했다. [0.6.2 핫픽스](HOTFIX_0.6.2.md)에 재현·회귀
검사를 기록했다. 최종 빌드에서는 일부 성공 사례만 골라 합치지 않고
네 문항 × 네 구성을 모두 다시 실행한다. 앞선 진단 기록은 별도로 보존한다.

## 최종 설치본 실측

| 구성 | 정답 / 시도 | 완료 시간 중앙값 | 평균 완료 시간 | 평균 입력+출력 토큰 |
| --- | --- | --- | --- | --- |
| 단일 | 4 / 4 | 15.25초 | 20.70초 | 17,604.75 |
| 관계 메모리 | 4 / 4 | 13.33초 | 20.75초 | 21,579.75 |
| 오케스트레이션 | 3 / 4 | 36.41초 | 67.67초 | 미상: 시간초과 사용량 불완전 |
| 둘 다 | 4 / 4 | 29.51초 | 39.23초 | 15,414.00 |

최종 실행 16건 중 15건이 답을 완료했고 모두 정답이었다. 회의만 사용한
I-06은 답변 텍스트 없이 180.08초에 취소됐다. 실패를 분모와 시간 통계에서
제외하지 않는다. 부분 사용량은 있으나 취소된 작업의 전체 토큰이 확인되지
않아 회의 구성의 평균 토큰을 0이나 완료한 3건의 평균으로 대신하지 않았다.
중앙값은 짝수 표본에서 가운데 두 값의 산술평균이다.

모든 성공 응답의 최종 경로와 실패 응답의 관측 공급자 모델은 `gpt-6-sol`이다.
각 회의 요청에서 독립 풀이 시작 이벤트 2개씩, 단일 요청에서는 네이티브
실행 시작 1개씩을 확인했다. 이는 CLI 내부 총 추론/도구 요청 횟수와 다르다.
단일과 메모리 구성의 I-06에서 네이티브 명령 실행 활동이 관측됐다.

첫 답변 텍스트 중앙값은 단일 8.91초, 관계 메모리 10.30초, 결합 29.40초다.
회의만 사용한 구성은 한 요청에 텍스트가 없었으므로 네 요청 전체의 값을
제시하지 않는다. 이 값은 작업 상태 메시지나 내부 추론 이벤트의 시작 시간이
아니다. 텍스트 경로는 응답 포맷 처리 방식도 네이티브 경로와 다르다.

이 표본에서 관계 메모리가 정답률을 높였다는 증거는 없었다. 결합은 단일보다
보고된 평균 입력+출력이 약 12.4% 적었지만 평균 완료 시간은 약 89.6% 길었다.
캐시 입력 비율과 계산 도구의 사용 여부가 다르므로 **일반적인 비용 절감률이나
최적 구성으로 승격하지 않는다.** 간단한 작업까지 항상 회의시키는 근거도 없다.

## 해석의 한계

- 네 문항의 소규모 파일럿이다. AIME 한 해 전체 점수, 공식 리더보드,
  취약점 탐색·브라우저 작업·일상 보조의 일반 정확도가 아니다.
- 공개 문제의 학습 포함 가능성이 있고 앞선 진단에 사용했다. 신규 holdout
  성능이나 반복 안정성을 입증한 것이 아니다.
- 단일 구성은 계산 명령을 사용할 수 있는 네이티브 경로, 회의 구성은
  도구 없는 CLI 텍스트 경로다. 권한 설정은 같지만 실행 방식·문맥량·출력
  전달 방식은 다르다. **앱 구성 전체의 비교이지 오케스트레이션만의 순수
  인과 효과가 아니다.**
- 입력 토큰에는 보고된 캐시 입력이 포함된다. 구독 비용이나 과금액으로
  환산하지 않는다. 첫 텍스트는 상태/진행 안내가 아닌 답변 텍스트 기준이다.
- 회의 시작 이벤트와 최종 모델 경로는 확인하지만, 네이티브 CLI 내부의
  모든 공급자 요청 횟수는 앱이 노출하지 않아 총 호출 수로 단정하지 않는다.
- 네 문항으로 자동 정책을 승격하거나 항상 회의하도록 바꾸지 않는다.
  실패·불확실성 검증에 대한 더 큰 반복 평가가 필요하다.
- 사용 중인 PC와 외부 구독 서비스에서 측정했다. 프로세스 시작·캐시·서버
  부하의 변동을 없앤 전용 벤치마크 장비의 측정은 아니다.

실행 식별자·로컬 경로·문제 원문·정답·개별 예측 정수·원시 대화·자격증명은

## 0.6.3 후속 검사: 느린 노드 대기 복구

앞서 회의형에서 시간초과된 **2022-AIME-I-06 한 문항**을 네 구성으로
각 한 번 재실행했다. 실제 설치 앱의 동일한 `chat.start`, 정확한
`gpt-6-sol`, medium, Daybreak 꺼짐, 작업공간 권한, quality 예산,
180초 호출자 제한, 동일 문제·프롬프트·정답 판정을 사용했다.
실행 순서는 단일 → 회의 → 관계 메모리 → 결합이다. 신규 holdout이나
네 문항 전체의 재측정이 아니며, 위의 0.6.2 실패 기록은 대체하지 않는다.

| 구성 | 0.6.2 해당 문항 | 0.6.3 해당 문항 | 이번 판정 |
| --- | ---: | ---: | --- |
| 단일 | 42.7초 | 96.7초 | 정답 |
| 관계 메모리 | 49.8초 | 41.0초 | 정답 |
| 오케스트레이션 | 180.1초·시간초과 | 94.2초 | 정답 |
| 결합 | 72.1초 | 121.7초 | 정답 |

회의형에서는 B 노드가 54.2초에 완료됐다. A 노드는 끝나지 않았지만
15초 유예 후 중단했고, **69.3초에 최종 검증을 시작**해 94.2초에
정답을 반환했다. 결합에서도 B가 47.0초에 완료, A는 62.1초에 중단,
최종 검증 후 121.7초에 정답을 반환했다. 노드별 실제 모델·상태·경과
시간이 앱의 비공개 실행 기록에 남은 것도 확인했다.

최종 검증자는 이제 단일 실행과 같은 네이티브 작업공간 도구 경로를
사용한다. 분석 노드들은 계속 도구 없이 실행한다. 따라서 이 결과는
**지연 노드가 최종 검증을 막던 현상의 복구 증거**이지, 모든 구성이
빨라졌다거나 오케스트레이션의 순수 성능 향상을 입증하는 결과는 아니다.
실제로 이번 단일·결합 시간은 이전보다 길었다. 모델·캐시·공급자 부하의
변동과 실행 경로 차이를 통제한 반복 검사는 별도로 필요하다.
취소 노드의 완전한 실제 토큰 보고가 없으므로 비용 절감률은 계산하지 않는다.

추가 회귀 테스트 14개(지연·전체 실패·취소·입장 예산·늦은 응답·이전
증거 보존·그룹 병렬·권한·진행 표시 장애), 기존 관련 테스트, 전체
타입 검사 및 Windows 설치 파일 빌드를 통과했다. 기본 공급자·라우팅·
플러그인 활성 상태를 유지하고 이번 시험용 관계 메모리 12개만 제거했다.
실행 중인 작업 0개, 남은 메모리 0개, 저장된 최종 답변 4개의 원문 일치를
확인했다. 결과는 앱의 `오케스트레이션 개선 검증 · Sol 6 · 0.6.3`에 있다.

검증한 설치 파일 SHA-256:
`e8b3cabd4c801caac6aef31c6ed84a768a98e4ee9839f43c19188d914d608f91`.
설치된 파일과 빌드 산출물의 `app.asar` SHA-256(검사 후 동일):
`565ba950c537ae094b400404707df01a4d6f18380d96a40fed7d9f568514a7b4`.
후속 프로토콜 SHA-256:
`ddb67dcea392e4cba8feaa400dab12bab6fb2123279607d437dcfb242c833d1b`.
후속 원시 보고서 SHA-256:
