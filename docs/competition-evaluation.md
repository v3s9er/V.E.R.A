# 대회 문제 기반 회귀 검사

검사기는 V.E.R.A의 실제 `AgentLoop`와 격리된 Codex 구독 전송 경로를 사용한다. 공식 대회 참가·리더보드 제출·앱 전체 성능 평가가 아닌, 조건을 고정한 자체 회귀 검사다. 앱의 기본 모델·권한·프로필이나 사용자의 대화는 변경하지 않는다.

실제 실행 집계는 [2026-10-02 결과](COMPETITION_RESULTS_2026-10-02.md)에 기록한다.

## AIME: 고정된 정답으로 확인하는 수학 추론

[AIMO 공개 검증 데이터](https://huggingface.co/datasets/AI-MO/aimo-validation-aime)의 2022~2024년 AIME I·II 문제를 사용한다. 실행할 연도를 정하면 I 15개, II 15개 **30문항 전부**를 고정 순서로 푼다. 잘 맞힌 문항만 선택하거나 실패 문항을 분모에서 빼지 않는다.

- 데이터셋: `AI-MO/aimo-validation-aime`
- 고정 리비전: `13f9e12f613e720c2a2b2f345dd04b998a29494d`
- 원본 Parquet SHA-256: `025484a99fea498e7d0c3b0ee42afcbec0176405c19c5dbf557b9f6ca6445675`
- 변환 캐시 SHA-256: `24e50dcd3ba120e4eb0f605bb03bf778f5dc5d6ace59ebb0ed106be943c67838`
- 출처 카드의 선언 라이선스: Apache-2.0. 이는 데이터셋 유지관리자의 선언이며, 별도 원출처 자료의 권리까지 확대 해석하지 않는다. 문제·정답·해설 파일은 공개 저장소에 재배포하지 않는다.

모델 입력에는 문제 본문만 제공한다. 참조 정답·해설·출처 URL은 입력하지 않고, 검색·PC 파일·셸·개인 메모리·기존 대화도 제공하지 않는다. 평가 전용 경로에서 사용자가 선택한 정확한 모델의 제공 여부를 먼저 확인하며, 이용 불가를 오답으로 기록하거나 다른 모델로 대체하지 않는다. Daybreak는 이 수학 검사에서 꺼져 있다.

채점 규칙은 실행 전에 고정한다. 최종 출력 전체가 `Answer: N` 형식이고 N이 0~999인 정수이며 참조 정답과 같아야 통과한다. 앞쪽 0은 허용하지만 후보 여러 개, JSON, 수식, 설명 속 정답 부분 일치는 허용하지 않는다. 형식 오류도 실패다. 정답 숫자를 생성했는지 검사하는 것으로 풀이 과정의 타당성까지 증명하지는 않는다.

각 문항은 새 CLI·새 세션에서 1회 실행한다. 기본 제한은 120초, 동시 실행은 1개, 재시도는 없다. 시간 초과는 분모에 남기고 다음 문제로 진행한다. 인증·전송·실행 불변식 오류는 추가 소비를 중단하며 미실행 문항 수를 별도로 표시한다. 실행 중 관련 소스의 해시가 바뀌면 비교 가능한 결과로 취급하지 않는다.

정답 수/전체 수, 완료 수, 실패 종류, 실제 추론 단계, 첫 텍스트·완료 시간 p50/p95, 보고된 토큰을 기록한다. 제공되지 않은 토큰 수는 0이 아닌 미상으로 보존한다. 완료 시간은 세션을 재사용하는 평소 대화의 지연과 직접 비교할 수 없다.

### 재현

Node 의존성과 `npm run build:shared`가 준비된 저장소 루트에서 실행한다. Python 3.12와 `pyarrow==21.0.0`은 데이터 준비에만 필요하다. 아래 설치는 전역 Python 환경이 아니라 Git에서 제외된 평가 폴더에 한정한다.

```powershell
python -m pip install --target release/validation/aime-tools pyarrow==21.0.0
$previousPythonPath = $env:PYTHONPATH
try {
  $env:PYTHONPATH = (Resolve-Path -LiteralPath 'release/validation/aime-tools').Path
  python scripts/benchmark-aime-prepare.py --out release/validation/aime-pinned.json
} finally { $env:PYTHONPATH = $previousPythonPath }

npm run test:benchmarks
npm run benchmark:aime -- --help
# 기존 구독 사용량을 사용하는 단계. 모델/추론/출력 경로를 명시한다.
npm run benchmark:aime -- --cache release/validation/aime-pinned.json --year 2024 --model gpt-6-sol --effort auto --allow-account-usage yes --timeout-ms 120000 --out-prefix release/validation/aime2024-run-001
```

캐시가 이미 존재하면 준비 명령은 덮어쓰지 않고 중단한다. 검증된 기존 캐시는 재사용한다. 실행 결과도 기존 접두사에 덮어쓰지 않으므로 새 실행마다 새 `--out-prefix`를 선택한다. Windows에서 `python`이 Store 별칭이면 실제 설치된 Python 실행 파일의 전체 경로를 사용한다.

결과는 `.manifest.json`, `.progress.jsonl`, `.report.json`으로 저장한다. 실행 중간 결과가 남고 참조 정답·원문 응답·개인 경로·인증정보는 결과에 싣지 않는다. 데이터 캐시와 원본 결과는 `release/validation/`에 보관하여 Git에서 제외한다. 공개 보고서는 검토된 집계치만 담는다. 원시 결과에는 예측 정수가 있으므로 캐시와 함께 별도 취급한다.

## 해석과 개선 원칙

- 공개 AIME 문제가 모델의 사전 학습에 포함되지 않았음을 보장하지 않는다. 다른 연도를 새로 실행해도 이는 이번 튜닝에서 미사용한 평가일 뿐, 모델 학습과의 독립성을 보장하는 비공개 시험은 아니다.
- 30문항의 Wilson 95% 구간은 문항 표본에 대한 참고치다. 서로 다른 날의 모델 변동·반복 실행 변동이나 모든 업무의 정확도를 나타내지 않는다.
- 재시도·프롬프트 변경 후의 성적은 별도 실험으로 기록한다. 최초 점수와 합치거나 가장 좋은 응답만 골라 pass@1이라고 부르지 않는다.
- 속도·정확도 향상 주장은 같은 문제·모델·조건의 기준/후보 비교와 별도의 미사용 평가로 확인해야 한다. 이 검사기는 평가 결과를 보고 프로덕션 설정을 자동으로 승격하지 않는다.
- 수학 검사에 더해 [BFCL 도구 호출 검사](external-agent-benchmarks.md)가 있다. 이 둘만으로 Discord 첨부·모바일 UI·컴퓨터 조작·장기 기억이 검증됐다고 주장하지 않는다.

과제별 목표, 고정 평가 기준, 지속적인 회귀 검사는 [OpenAI의 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)을 참고했다.

## AI TOP 100: 확인한 범위와 아직 없는 재현 자료

2026-10-02에 확인한 카카오 원문에는 [PDF의 숨겨진 텍스트](https://brunch.co.kr/@andkakao/322), [규칙 기반 입국 심사](https://brunch.co.kr/@andkakao/327), [코드 이미지 해석](https://brunch.co.kr/@andkakao/317), [영상 사실 확인](https://brunch.co.kr/@andkakao/324) 등의 유형이 있다. 따라서 추론 모델만이 아니라 첨부 원본 전달, 이미지·영상 관측, 규칙 우선순위, 출력 정합성이 필요하다.

확인한 소개 페이지에서는 숨겨진 텍스트 PDF 원본, 전체 입국 규칙·지원자 자료와 공식 정답을 확보하지 못했다. 과거 문제 허브 주소는 현재 대회 안내 페이지로 연결된다. **AI TOP 100 원문 전체를 실행하거나 공식 점수를 받았다고 표시하지 않는다.** 소개를 보고 만든 유사 문제는 별도의 합성 회귀 검사로 표기해야 하며 원문 대회 점수에 섞지 않는다. 원본 입력·채점 기준·이용 조건을 확인한 유형부터 확장한다.

### 2026-10-02: 실제 설치 앱으로 공개 코드 이미지 풀이

추가 조사에서 [카카오 공식 공개 문제](https://brunch.co.kr/@andkakao/317)의
`문제 자료`에 있는 코드 이미지 두 장을 확보했다. 샘플 정답 이미지는 사용하지
않았다. [공식 대회 소개](https://aitop100.org/about)는 기존 챌린지 사이트가
2026년 9월에 운영을 종료했다고 명시한다. 따라서 이번 결과는 사이트에 제출한
공식 점수가 아니라 **공개 과제 하나의 두 이미지 변형에 대한 로컬 검증**이다.

각 이미지에 언어 선택·일반 입력의 출력·지정 입력의 출력이라는 동일한 세 질문을
적용해 여섯 답안값을 비교했다. 여섯 개의 독립 대회 문제를 풀었다는 의미가 아니다.
코드의 두 이미지가 서로 다르므로 임의로 합치거나 수정하지 않도록 지시했다.

설치된 **Mr.Robot 0.6.3의 인증된 `chat.start`**를 사용했다. 직접 CLI 호출,
별도 AgentLoop 인스턴스, 컴퓨터 유즈로 우회하지 않았다. 모든 모델 노드는
`gpt-6-sol`, medium, Daybreak 꺼짐, 작업공간 권한, quality 예산을 사용했다.
호출자 제한은 각 420초였으며 실제로 시간초과된 실행은 없었다. 각 구성은 새로운
프로젝트와 대화에서 한 번만 실행했고 순서는 단일 → 회의 → 메모리 → 결합이다.

| 구성 | 일치한 답안값 | 완료 시간 | 첫 응답 텍스트 |
| --- | ---: | ---: | ---: |
| 단일 모델 | 5/6 | 166.2초 | 163.4초 |
| 오케스트레이션 | 6/6 | 350.9초 | 346.7초 |
| 관계 메모리 | 3/6 | 260.5초 | 256.6초 |
| 관계 메모리 + 오케스트레이션 | 2/6 | 101.5초 | 98.2초 |

**회의형만 이번 여섯 답안값을 모두 맞혔다.** 그러나 단일보다 오래 걸렸으며,
메모리나 결합이 항상 유리하다는 결과도 아니다. 한 번씩 실행한 동일 과제의
소규모 비교이므로 정확도·속도 차이의 인과관계나 전체 대회 성능으로 일반화하지 않는다.
순서에 따른 캐시·프로세스·공급자 부하 영향도 통제하지 않았다.

관계 메모리는 파일 구분·질문·입력 조건을 나타내는 여섯 개의 범위 한정 관계이며,
정답이나 해결 절차를 넣지 않았다. 완전한 온톨로지 추론 엔진의 성능으로 표현하지
않는다. 회의형의 분석 노드 둘은 텍스트 전용이고 최종 검증자만 네이티브 파일 도구를
사용한다. 따라서 세 노드가 이미지를 각각 관측하는 병렬 시각 분석 실험도 아니다.

채점 기준은 원본을 별도로 판독한 뒤 허용된 연산만 실행하는 CPython 검사로
만들었으며 모델에는 제공하지 않았다. 처음의 실행 의미 부분 검사에 더해,
구문 오류를 주장한 답변을 검증하기 위해 두 번째 이미지 전체를 전사하여
AST 파싱과 제한된 실행을 확인했다. 주장된 잘못된 기호는 원본 확대본에 없었고
독립 검사 결과는 기존 기준과 일치했다. 이 기준은 공식 정답표가 아니며 수동 전사의
한계가 있다. 대회 원본 이미지와 전사·정답·원시 대화는 Git 제외 영역에만 보관한다.

관측한 실패와 후속 검사 지점:

- 단일 실행은 두 번째 이미지의 분기를 첫 번째와 동일하게 오독했다.
- 메모리 실행은 원본에 없는 구문 오류를 보고해 해당 이미지의 세 답을 틀렸다.
- 결합 실행은 문자열 출력 인자와 이미지 간 차이를 오독했다.
- 네 구성 모두 **네이티브 모델 입력의 이미지 SHA-256이 다운로드 원본과 일치**했다.
  파일 전달 누락이나 두 파일을 같은 이미지로 교체한 현상은 이 실행에서 없었다.
- 네이티브 호출 기록에는 각각 5/15/14/4개의 도구 호출 묶음이 있지만 앱 telemetry의
  `toolCalls`는 모두 0이었다. 이 수치를 실제 도구 사용량으로 해석해서는 안 되며,
  관측 정확도 회귀 검사 대상이다. 호출 묶음은 개별 도구 호출 수와도 다르다.
- 코드 원문 인식 결과를 재확인하고 실제 파서/실행 검증으로 연결하는 절차가 필요하다.
  이번 실패를 없던 것으로 만들거나 성공한 재시도로 대체하지 않는다.

네 최종 답변의 앱 저장 일치, 원본 이미지 보존, 정확한 모델 경로를 확인했다.
시험용 메모리 12개를 제거한 뒤 남은 시험 메모리 0개·실행 중 작업 0개였다.
기본 공급자·라우팅·플러그인 상태는 변경하지 않았다. 네 작업공간과 대화는 앱의
`카카오 코드석판 · single/orchestration/memory/combined` 프로젝트에 그대로 남았다.
시험 중 생성했으나 사용하지 않은 빈 결과 프로젝트 하나만 연결 해제했고 파일은
삭제하지 않았다. 이번 검사는 앱 코드 수정이나 새 버전 배포를 포함하지 않는다.

재현 자료 해시(비공개 원시 자료의 동일성 확인용):

시청각 근거를 검증하지 않아 실행·채점 결과에 넣지 않았다. 다른 동명 문서나
유사 자료로 대체해 기출을 풀었다고 계산하지 않았다.

### 0.6.4: 관측 경로 수정과 실패를 보존한 재검사

같은 원본·질문·모델(`gpt-6-sol`)·medium·Daybreak 꺼짐·420초 제한을
사용했다. 모든 실행은 설치된 데스크톱 앱의 인증된 `chat.start`를 통과했다.
각 개정판은 새로운 프로젝트/대화에서 실행했으며 이전 실패를 덮어쓰지 않았다.

첫 후보는 읽기 전용 원본/확대/문법 검사 도구와 실제 이미지 전달, 네이티브 도구
집계를 추가했다. 그러나 과도한 재검사로 단일 실행이 시간초과되고, 회의 노드가
허용 단계를 모두 자료 요청에 써서 관측 결과를 반환하지 못하는 문제가 드러났다.
후속 r2는 마지막 단계를 결과 전달에 예약하고, 동일 세션의 중복 이미지 전송을
제거하며 최소한의 결정적 검사를 우선하도록 수정했다.

| --- | --- | --- | --- |
| 단일 | 5/6 · 166.2초 | 시간초과 · 420.3초 | 5/6 · 153.8초 |
| 회의 | 6/6 · 350.9초 | 6/6 · 341.7초 | 3/6 · 330.4초 |

시간초과는 정답 0/6으로 분모에 남는다. 첫 후보의 두 회의 구성은 검토 노드가
모두 실패해 최종 검증자가 독자적으로 완료한 것이므로 병렬 성공으로 세지 않는다.
r2 회의형은 한 노드 완료 후 다른 노드를 유예 시간에 따라 종료했고, 결합형은
두 노드가 모두 완료했다. r2 회의형은 잘못 전사한 문법을 원본 오류로 간주했다.
**파서가 전사본을 검사했다는 사실은 원본 판독의 정확도를 보증하지 않는다.**

기출 한 과제의 반복 튜닝이며 각 칸은 단 한 번의 실행이다. 홀드아웃 평가나
공식 대회 점수가 아니다. 캐시·공급자 부하·실행 순서뿐 아니라 일부 실행 중
같은 호스트의 빌드/회귀 검사 부하도 통제하지 않았다. 속도나 정확도가 일반적으로
향상됐다고 주장하거나 성공한 구성만 합쳐 성적을 발표하지 않는다.

두 개정판 모두 원본 파일 해시 보존과 네이티브 도구 결과의 원본 식별자,
실제 이미지 입력, 완료 답변의 앱 저장 일치를 확인했다. r2 앱 이벤트의 도구 시작
수 21/30/17/25가 telemetry와 일치한다. 이는 네이티브 호출 묶음과 호스트 관측
호출의 계수이며, 모델 내부의 모든 연산 개수를 뜻하지 않는다. `toolElapsedMs`는
동시 호출이 겹칠 수 있는 합산 시간으로 전체 지연 시간과 구분한다.

원시 자료는 계속 Git 제외 영역에만 보관한다.

#### 최종 설치 개정 r3: 원본별 분담

r2 회의형의 퇴행을 숨기지 않고, 서로 다른 원본을 모든 노드가 중복 판독하는
흐름을 변경했다. 명시된 로컬 PNG를 최대 네 장까지 노드별로 나누고 처음부터
실제 픽셀을 전달한다. 각 읽기 도구는 배정된 파일만 허용한다. 상호 보완적인
분담에는 반수 완료 기준을 사용하지 않고 모두 완료하거나 기존 제한 시간까지
기다린다. 노드 75초·전체 회의 90초 제한, 모델·추론 강도·그래프는 유지했다.

영향을 받는 회의·결합 구성만 같은 과제로 다시 실행했다. 이 개정의 실측 중에는
빌드/전체 회귀 검사를 동시에 돌리지 않았다.

| --- | ---: | ---: | --- |

두 구성 모두 두 번째 원본의 마지막 출력값을 틀렸다. 따라서 **전체 부족점이

6/6이었던 결합형도 r3에서는 5/6이었다. 원본 판독과 문자 연산의 정합성, 제한

해결되지 않으며, 별도의 미사용 시각 과제와 반복 측정으로 확인해야 한다.

앱 저장 답변 일치, 원본 해시 보존, 네이티브 이미지 입력을 확인했고,
도구 시작 이벤트 28/29개와 telemetry가 일치했다. 기본 공급자·라우팅·플러그인
설정은 유지했다. 총 10개 실험 대화/작업공간과 원본/실패 기록은 보존했으며,
시험용 관계 메모리는 모두 제거했다. 세 개의 비어 있는 결과 프로젝트 등록만
연결 해제했고 디스크 파일은 삭제하지 않았다. 종료 후 활성 작업은 0개였다.

일반 대화 회귀도 별도로 확인했다. 같은 설치 앱·Sol 6·medium으로 단순 산술
질문과 직전 답을 참조하는 후속 질문을 보냈다. 각각 3.898초/1.993초에 정확한
숫자 답변이 도착했고 두 번째 요청에서 세션 재사용이 관측됐다. 이는 두 번의
기능 점검이며 일반 업무의 평균 지연이나 기출 정답률에 합산하지 않는다.

### 온톨로지 구현 후 실제 앱 비교 (0.6.4 후속 개정)

이제 관계 메모리만이 아니라 [제한된 온톨로지 엔진](ontology.md)을 사용한다.
분류 상속·전이 관계·단일 값 충돌·모순 유형·순환 검사가 로컬에서 수행되고,
근거 ID와 규칙을 포함한 문맥이 단일 실행과 회의 실행 모두에 전달된다.
전체 OWL/SHACL 구현이나 모델 가중치 학습은 아니다.

새 합성 사실 18개와 질문 10개를 사용했다. 네 구성 모두 동일한 사실 목록과
규칙 정의를 사용자 요청으로 받았고, 온톨로지 구성에만 같은 사실을 범위 지정
메모리로 추가했다. 정답은 제공하지 않았다. 각 구성을 두 번 실행하고 두 번째
순서를 뒤집었다. 매번 새 프로젝트·대화였으며 설치 앱의 인증된 `chat.start`,
`gpt-6-sol`, medium, Daybreak 꺼짐, 기존 2검토자+최종 검증 경로를 유지했다.

**정확도 향상은 입증되지 않았다.** 원래 단일 모델도 모두 정답이었다. 온톨로지
단일 실행의 평균 입력은 약 14.5% 늘었다. 두 번뿐인 시간 차이로 속도 우위를
주장하지 않으며, 이 과제에서 회의는 정확도 이득 없이 비용·지연을 늘렸다.
따라서 기본 실행을 일괄 회의형으로 전환하지 않았다. 캐시 적중과 공급자 부하는
통제되지 않았고, 사전 `memory.inspect`가 로컬 검색 캐시를 데웠다. 합성 기능
검사이며 독립 홀드아웃·대회 점수나 80개의 독립 과제로 세지 않는다.

### 0.6.4 데스크톱 빈 창 복구 개정

위의 백엔드 점검만으로 실제 창 표시를 확인하지 못했던 누락을 보완했다.
