# 이미지 판독·값 검산 후속 검사 — 2026-10-02

## 변경과 근거

기존 개발 회귀 사례에서는 작은 문자를 다르게 읽거나 여러 열의 코드 실행
순서를 바꿔, 두 회의 구성 모두 여섯 답 항목 중 하나를 틀렸다. 문법 검사만
통과한 것을 실제 출력 검증으로 취급할 수 없었다.

이번 수정은 원본 좌표를 보존하는 정수 배율 확대와 제한된 정확 계산기를
연결한다. `evidence_python_values`는 전사한 최소 대입문·문자열 연산을
고정 AST 해석기로 검산하고, 각 갱신 값과 줄 번호를 반환한다. 이미지가
올바르게 전사됐다는 보증은 아니며, 임의 프로그램 실행 도구도 아니다.
원본 관찰·전사·계산 결과의 경계를 유지한다.

[OpenAI 이미지 가이드](https://developers.openai.com/api/docs/guides/images-vision)의
작은 글자·리사이징 한계를 반영해 인접 행을 포함한 확대 관찰을 지원했다.
Responses API의 옵션을 지원 여부가 다른 CLI 프로토콜에 임의로 넣지는 않았다.
[평가 가이드](https://developers.openai.com/api/docs/guides/evaluation-best-practices)에
따라 기존 오답 재현 검사와 새 합성 전이 검사를 구분한다.

- 이 과제의 결합형은 사실 6개·추론 0·충돌 0이다. 새로운 온톨로지 추론
  능력의 우월성을 이 시험으로 주장하지 않는다.

네 후속 실행 모두 **6/6** 답 항목이 독립 기준과 일치했다. 기존 이미지
오답은 이 두 번씩의 재검사에서 재현되지 않았다. 그러나 속도 향상은
입증하지 못했다. 검토자 8회 중 3회가 75초 한도에 걸렸고 최종 검증자가
누락 부분을 다시 확인했다. 이 지연을 해결 완료로 표시하지 않는다.

회의형의 보고 입력/출력/캐시 입력 토큰은 반복 1에서
501,384 / 8,619 / 386,688, 반복 2에서 851,031 / 7,264 / 772,736이었다.
결합형은 553,483 / 8,530 / 478,976 및 737,391 / 8,712 / 632,192였다.
캐시 입력은 총 입력에 포함되므로 다시 더하지 않는다. 중단 노드의 전체
사용량을 알 수 없고 여러 호출 누적값이므로 문맥 창 크기나 청구액도 아니다.
토큰 효율 향상의 증거로 삼지 않는다.

모든 최종 답변은 앱 저장본과 일치했고, 다른 모델로 대체되지 않았다.
시험용 사실만 제거한 뒤 공급자·기본 라우팅·플러그인 설정이 그대로이며
활성 실행이 0개임을 두 보고서에서 확인했다.

두 코드 이미지는 한 공개 과제의 변형이다. 여섯 답 항목은 여섯 개의 독립
문제가 아니다. 개발 중 이미 확인한 실패 사례이므로 새 holdout이나 대회
전체 정확도로 해석하지 않는다. 공식 답안이 아니라 독립 판독과 제한된
CPython 실행으로 확인한 자체 기준이다.

실행은 사용 중인 PC와 구독 서비스에서 이루어져 캐시·공급자 부하를 통제하지
못했다. 두 번째 반복 중 새 합성 이미지 두 장을 만드는 짧은 로컬 렌더링도
있었다. 입력 토큰에는 캐시 입력이 포함되며 중단 검토자의 사용량은 완전하지
않을 수 있으므로 비용 절감률을 계산하지 않는다. 기본 단일 실행은 유지한다.

## 새 합성 문제에서 발견한 누락과 후속 변경

기출 재검사 뒤 정답 문자열이 다른 다열 코드 이미지 두 장을 새로 만들었다.
기준 답은 제품의 계산기가 아닌 별도 CPython 실행으로 확인했다. 같은 질문,
같은 Sol 6, 네 구성 각각 1회, 매번 새 프로젝트로 검사했다.

| 구성 | 최초 전이 검사 | 완료 시간 |
| --- | ---: | ---: |
| 단일 | 4/6 | 33.624초 |
| 온톨로지 | 6/6 | 44.109초 |
| 회의 | 6/6 | 60.080초 |
| 온톨로지+회의 | 6/6 | 62.550초 |

단일 실행은 일부 갱신문을 빠뜨리고 그 잘못된 전사를 정확히 계산했다.
원본 첫 행에서 덮어쓴 값을 제거하는 것과, 이후 같은 열의 유효한 갱신문을
제거하는 것을 혼동한 사례였다. 계산기 성공만으로 이미지 이해 성공을
주장할 수 없음을 이 실패가 보여준다. 최초 결과는 그대로 보존한다.

출력 값의 도달 가능한 의존 관계를 먼저 확인하고, 마지막 관련 초기화부터
이후의 모든 갱신을 원본 행과 대조하도록 지침을 보완했다. 별개 코드 조각을
합치지 않으며, 같은 Python 행의 세미콜론 문장만 왼쪽부터 읽게 범위를
명확히 했다. Code Mode에서 이미지 결과를 MCP `content[]`로 오인해 다시
읽는 사례도 있어, 문자열 결과의 메타데이터/이미지 URL 형식을 도구 설명에
명시했다. 원본·답안·특정 문자열을 제품 지침에 넣지 않았다.

최초 전이 검사 보고서:
`09747a756a9ca8c45ed7f82f46f2915d24b51c2cca3e2c7ba0a4a07a229ee41d`.
해당 설치 번들:
`066bedadf8b797b67d6a422cc20c87d0fbee8bd292ba9d12d05e2b3645bca684`.

지침 보완 후 같은 문제를 역순으로 재검사한 r2는 단일/회의/결합 6/6,
온톨로지 단독 5/6이었다. 값과 갱신 위치를 바꾼 새 이미지 두 장의 r3도
같은 점수 분포였다. r2 시간은 각각 27.848/53.092/60.939/21.939초,
r3는 24.639/96.366/42.785/23.497초였다(앞 문장의 구성 순서).
r3 회의의 검토자 하나가 시간 제한에 걸린 사실도 그대로 기록한다.
이 결과로 지침만 바꾸면 관측 오류가 해결된다고 주장하지 않는다.

도구 호출 내용을 원본과 대조하니 일부 슬라이스의 대괄호·콜론을 잘못
옮긴 상태에서 계산은 올바르게 수행됐다. 후속 개선은 여백 처리다. 네 모서리
RGBA가 같고 외곽 픽셀이 정확히 같은 색인 경우에만, 모든 다른 픽셀과
12픽셀 여유를 보존하여 큰 균일 여백을 뺀다. 추정 배경 제거/OCR/재생성은
하지 않는다. 의미 있는 면적 감소가 없으면 원본을 유지한다.

명시적 crop은 변경하지 않으며 `trim:false`로 원래 캔버스를 받을 수 있다.
원본 크기·해시·좌표와 실제 표시 영역을 함께 반환한다. 합성 시험 이미지는
2800×720→1136×438로 줄어들었지만 모든 비배경 픽셀 값은 그대로였다.
작은 기호가 넓은 빈 캔버스 때문에 축소되는 상황을 줄이려는 개선이며,
픽셀 보존 검사가 모델의 올바른 판독을 보장하지는 않는다.

여백 처리를 적용한 설치본의 두 개발 재검사 결과는 다음과 같다. 새 세션을
사용했고 실행 순서를 바꿨으며, 실패한 구성만 골라 다시 실행하지 않았다.

| 구성 | r4 · 첫 합성 묶음 | r5 · 두 번째 합성 묶음 |
| --- | ---: | ---: |
| 단일 | 6/6 · 60.453초 | 6/6 · 21.675초 |
| 온톨로지 | 6/6 · 24.038초 | 6/6 · 22.641초 |

| 온톨로지+회의 | 6/6 · 55.764초 | 6/6 · 75.338초 |

r4 회의의 최종 검증자는 확대 관찰 후에도 슬라이스를 다르게 전사했다.
반대로 r5의 네 구성은 모두 일치했다. r5 회의에서는 검토자 하나가 75초
한도에 걸렸다. 따라서 여백 처리만으로 관측 오류나 긴 꼬리 지연을 제거했다고
하지 않는다. r2–r5 단일 실행의 연속 성공도 작은 개발 세트 결과일 뿐이다.

추가 OCR 경로는 실험 단계에서 보류했다. Windows 언어 엔진은 조회됐지만
고정 보조 프로세스의 시작이 `EPERM`으로 실패했다. 실행 정책을 우회하거나
미검증 OCR을 제품 경로에 추가하지 않았다. OCR 결과가 원본보다 정확하다는
가정도 하지 않는다. [Windows OCR API](https://learn.microsoft.com/en-us/uwp/api/windows.media.ocr.ocrengine)
검토는 구현 채택이나 실제 OCR 성공을 의미하지 않는다.

## 마지막 미사용 변형 검사: 일반화 실패도 보존

제품 코드를 고정한 뒤 변수·문자·갱신 위치를 다시 바꾼 두 이미지를 만들고,
별도 CPython으로 답을 확인한 다음 처음으로 네 구성에 제공했다(r6).
정답은 작업공간 밖에 뒀고, 모든 질문/모델/권한/시간 제한은 동일했다.
실행 순서는 결합→온톨로지→단일→회의였으며 실패를 대체 재시도하지 않았다.

| 구성 | 정답 항목 | 완료 시간 | 입력 / 출력 / 캐시 입력 토큰 |
| --- | ---: | ---: | --- |
| 단일 | **5/6** | 28.030초 | 40,455 / 775 / 33,920 |
| 온톨로지 | **5/6** | 108.281초 | 41,696 / 746 / 34,944 |
| 회의 | **5/6** | 44.850초 | 72,561 / 2,035 / 47,488 |
| 온톨로지+회의 | **5/6** | 47.438초 | 78,017 / 2,117 / 63,488 |

네 구성 모두 같은 항목에서 같은 오답을 냈다. 단일 실행의 실제 계산기 입력을
대조해, 원본의 `z[:-1]`을 `z[::-1]`로 전사했음을 확인했다. 계산기는 전달받은
다른 프로그램을 정확히 계산했지만 원본 판독을 교정하지 못했다. 다수의
일치나 온톨로지의 존재를 정확성 보증으로 취급하면 안 되는 사례다.

따라서 **기존 회귀 사례 개선은 확인됐지만 일반적인 이미지 정확도 개선은
입증되지 않았고, 판독 오류는 미해결**이다. 회의형을 기본값으로 올리지 않는다.
구성별 시간 편차도 커서 처리 속도 향상을 주장하지 않는다. 다음 개선은
같은 모델에게 같은 판독을 반복시키는 대신 독립 관측 수단의 대조/불일치
감지부터 검증해야 한다. 이 보고서는 그 기능의 구현 완료를 뜻하지 않는다.

r6의 최종 응답은 앱 저장본과 일치했고, 정확한 요청 모델을 유지했으며,
설정 보존과 종료 후 활성 실행 0개를 확인했다. 정리 과정에서 시험 대화
27개만 보관하고, 사용자가 후속 대화한 1개는 그대로 남겼다. 비어 있던
시험용 등록 8개만 해제했으며 파일·실제 작업공간·원래 대화는 삭제하지 않았다.
시험용 메모리는 남아 있지 않다.

## 보안과 공개 범위

계산기는 import, 파일·네트워크 접근, 속성 접근, 임의 함수 호출, 반복문,
eval/exec/compile을 허용하지 않는다. 문자열·정수 크기, 소스/AST/문장 수,
평가 단계, 출력 크기와 프로세스 시간이 각각 제한된다. 부분 실행 결과는
검증 성공으로 반환하지 않는다. 모델이 쓸 수 있는 작업공간의 Python은
호스트 해석기로 선택하지 않는다. 이미지 도구의 경로·해시·픽셀 경계도 유지한다.

원시 대화, 계정/기기 식별자, 로컬 사용자 경로, 비밀 값, 기출 원본 이미지,
참조 정답은 공개하지 않는다. Git에는 구현·합성 단위 테스트·집계만 넣는다.

## 코드·설치 검증

- 최종 이미지 처리 코드에서 `npm test` 전체와 `npm run typecheck`를 통과했다.
  증거/회의/네이티브 도구 집중 검사 40개도 통과했다. 실제 모델 정답률과
  소프트웨어 단위 테스트 통과율을 혼동하지 않는다.
- 공개 소스·도달 가능한 Git 이력의 민감정보 패턴 검사를 통과했다.
  모든 비밀이나 취약점의 부재를 보장하는 완전한 감사라는 뜻은 아니다.
- 설치된 0.6.4 번들 해시를 실제 측정 프로토콜과 대조했고, 네이티브 앱에서
