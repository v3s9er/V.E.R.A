# 0.6.7 단순 응답 지연 검증 — 2026-10-03

## 범위와 절차

설치된 Windows 앱에 기존 로컬 관리자 인증으로 접속하여 `chat.start`를 호출했다. CLI를 직접 호출해 앱 실행처럼 보고한 시험이 아니다. 별도 합성 CLI 프로토콜 시험은 아래에 구분했다.

- 모델: 모든 실측 `gpt-6-astra`, 자동 대체 없음.
- 저장 설정: 추론 high, Daybreak 꺼짐, full 권한, quality 질문 예산. 검증 후 동일함을 확인했다.
- 실효 설정: 단순 요청만 low, 모델 및 PC 권한은 변경하지 않음.
- 한 라운드: 새 프로젝트 내 새 대화에 인사 → `2 + 2 =` → 직전 식과 답 반복. 5개 대화, 15회 호출.
- 변경 전 15회, 중간 빌드 15회, 최종 빌드 15회 + 재검증 15회. 총 60회 모두 응답 성공, 동일 모델, 스트림/최종 답 일치, 도구/보조 에이전트 0개, 계산 기억 유지, 설정 유지.
- 정확도 일반 평가가 아닌 응답 경로 회귀 시험이다. 단순한 세 요청으로 고난도 능력 향상을 주장하지 않는다.
- 실패/느린 샘플은 버리지 않는다. 내부 보고서는 덮어쓰지 않으며 개인 계정·대화·프로젝트 식별자가 포함된 원본은 Git 제외 경로에만 보관했다.

## 설치 앱 실측

초 단위 중앙값. 각 셀은 해당 종류 5회 측정이다. 첫 글자는 클라이언트가 실제 비어 있지 않은 `chat.delta`를 받은 시점이다.

| 요청 | 0.6.6 첫 글자 / 완료 | 0.6.7 최종 첫 글자 / 완료 | 같은 빌드 재검증 첫 글자 / 완료 |
|---|---:|---:|---:|
| 새 대화 인사 | 5.329 / 5.509 | 3.318 / 4.156 | 3.008 / 3.686 |
| 같은 대화 계산 | 2.520 / 2.722 | 1.628 / 1.983 | 1.503 / 1.907 |
| 직전 식과 답 반복 | 2.431 / 2.605 | 1.849 / 2.681 | 1.697 / 2.296 |

최종 30회의 첫 글자 범위: 인사 2.727–3.921초, 계산 1.346–3.182초, 반복 1.381–2.775초. 반복 응답의 첫 검증 완료 중앙값은 2.605→2.681초로 약간 증가했다. 모든 샘플이나 모든 지표가 개선됐다고 주장하지 않는다.

새 대화는 새 CLI 스레드다. 변경 전에는 각각 프로세스도 새로 생성했고, 변경 후에는 도구 없는 유휴 프로세스만 재사용했다. 앱 재시작 직후의 완전한 콜드 프로세스는 최종 검증 첫 라운드 1개다(첫 글자 3.318초 / 완료 4.028초). 재검증은 실행 중인 앱에서 진행했다. 모든 샘플을 콜드 부팅 측정으로 부르지 않는다.

무작위 교차 시험이 아니고 외부 서비스 상태를 통제하지 않았으므로, 측정된 차이 전체가 코드 변경만의 효과라고 단정할 수 없다. P95 보장 또는 항상 일정 시간 이하라는 주장은 하지 않는다.

### 중간 빌드도 보존

JSON 포장만 제거한 중간 빌드의 첫 글자 중앙값은 인사 4.480초 / 계산 1.986초 / 반복 1.533초였다. 인사의 느린 샘플은 첫 글자 7.495초 / 완료 8.628초였다. 5번째 새 대화에서 프로세스 퇴역 대기가 약 1.27초 발생하여 연결 재사용을 추가했다. 중간 측정은 최종 성능 수치에 섞지 않았다.

## 병목 분리

최종 최초 실행의 앱 시작→CLI turn 접수는 300ms였다. 이후 새 대화는 139–192ms, 같은 대화의 다음 요청은 11–25ms였다. 모델의 첫 델타를 받은 뒤 클라이언트에서 관측되기까지는 1–7ms였다(클라이언트/서버 측정 시작점 차이 포함).

주된 남은 대기는 CLI turn 접수부터 첫 모델 텍스트까지다. 이 구간에는 CLI 내부·네트워크·공급자 처리가 함께 포함되므로 OpenAI 추론 시간만이라고 분리해 주장하지 않는다. Astra의 확인된 최소 추론은 low였다. 미지원 none, 모델 자동 하향, 유료 우선 처리, 추가 예열 추론을 사용하지 않았다.

## 구현과 격리 조건

일반 텍스트 답변은 응답 JSON 스키마 없이 `item/agentMessage/delta`를 전달한다. 스키마가 필요한 도구 요청은 기존 프로토콜을 유지한다. 정상 완료 상태와 스트림/최종 본문의 일치도 계속 검증한다.

유휴 텍스트 프로세스만 동일 공급자·모델·실행 명령·환경 식별자 내에서 재배정한다. `thread/unsubscribe` 확인 후 새 `thread/start`를 수행하며, 이전 ID 재사용과 알 수 없는 스레드 출력을 차단한다. 이미 확인된 퇴역 스레드의 늦은 알림만 버린다. 이 순서는 [공식 Codex App Server 문서](https://learn.chatgpt.com/docs/app-server)의 초기화·스레드·스트림 수명주기를 따른다.

새 대화에는 새 스레드, 해당 대화의 정본 기록과 지침만 전달한다. 이미지 해시, 사용량, 이벤트 상관관계, 대화 기록은 재설정한다. 브로커와 네이티브 도구 프로세스는 재배정 대상이 아니다. 동시에 실행 중인 작업의 프로세스를 빼앗지 않는다. 16번 재배정 후에는 교체하며 유휴 만료 120초, 실행 슬롯 4개, 종료 핸들 대기를 유지한다.

## 회귀 검증

- 전체 `npm test` 및 PC/web/mobile 타입 검사 통과.
- 기존 구조화 텍스트 풀, 세션 이벤트, 네이티브 대화/조향/권한, 조정 실행, 모델 튜닝, 증거 도구, 모바일/원격 보안 회귀 포함.
- 새 일반 텍스트 시험: 완료 이전 출력, 누락된 델타 보완, 중복 완료, 여러 답변 항목, 대화 기억, 권한 지침 변경, 타 대화 출력, 도구 공격, 취소, 공급자 실패, 구독 해제 실패, 18개 스레드의 제한된 재사용 통과.
- 설치된 실제 Codex + 합성 loopback HTTP 공급자: 6개 새 스레드/프로세스 초기화 1회, 네이티브 도구 0개, 이전 사용자 입력 유출 0개, 스트림 일치. 계정 추론을 쓰지 않은 프로토콜 시험이며 모델 속도 점수는 아니다.
- 위 합성 시험의 첫 두 시도는 본 검증 후 Windows 임시 디렉터리 정리에서 EPERM이 발생했다. 제한된 재시도 정리를 추가한 뒤 전체 시험이 종료 코드 0으로 완료됐다. 해당 실패 로그도 보존했다. 첫 두 시도의 합성 데이터 임시 폴더는 후속 삭제가 실행 정책에 차단되어 남겨 두었다. 다른 방식으로 삭제를 우회하지 않았다.
- 최종 staged Electron UI 렌더링, 입력창 노출, 렌더러 강제 크래시 복구, 에이전트 PID 보존 통과.
- 개발 중 설치가 아직 끝나기 전에 시도한 첫 RPC 연결은 ECONNREFUSED였다. 모델 호출 전 실패이며 완료 후 정상 재시도했다. 이를 모델 실패나 성능 샘플로 계산하지 않았다.
