# 0.6.1 — Adaptive execution and Daybreak update

This update applies the pending Daybreak, adaptive orchestration, project context,
MCP efficiency and external-regression requirements. It does not replace model
weights, claim a leaderboard rank, or increase PC permissions.

## Implemented

- **Daybreak is an option, not a renamed model.** Desktop and mobile expose a
  separate toggle for GPT through Codex CLI or the official OpenAI API. Other
  providers hide it. The conversation persists the option; switching to an
  unsupported provider clears it. Active runs cannot change the option.
  Codex sends explicit `standard` or `daybreakBlue` in `turn/start`; provider
  entitlement remains authoritative. A selected legacy Red model uses Red only
  when explicitly enabled. Changing the option separates cached CLI sessions.
- **Model picker:** searchable grouped providers, selected-model indication,
  compact composer, provider filters; mobile's manual model-ID form is collapsed.
  Redundant legacy Daybreak aliases are hidden unless currently selected.
- **Adaptive execution:** no extra classifier model on the critical path. A
  lightweight initial depth hint selects low/medium/high for automatic reasoning;
  repeated tool failures escalate API/broker reasoning, successful progress can
  return to the initial depth. Explicit conversation reasoning wins. Complex work
  may use existing bounded independent helpers; simple tasks are instructed to
  answer directly. This is a heuristic, not a trained difficulty classifier.
  Native CLI internal steps are not claimed to be host-controlled mid-turn.
  Only recognized greetings, simple model-identity questions and arithmetic get
  the direct hint; short wording alone is not evidence that a task is easy.
  Authentication/environment errors do not increase reasoning effort.
- **Project instructions:** only the selected root's bounded `AGENTS.md` enters
  non-isolated context. It cannot grant permissions. No parent/home-wide scan.
- **Scoped knowledge:** optional project/conversation scope and provenance;
  subject/property/value facts can be entered in Settings. A replacement retains
  the old fact visibly but excludes it from recall. Zero-match retrieval abstains;
  another project's scoped facts are excluded. This is a small explicit fact
  store, not an autonomous graph database or unrestricted long-term memory.
- **Conversation compaction:** role-labelled historical excerpts preserve late
  constraints, evidence and unresolved items; transcripts remain the source of
  truth. No extra model call for compaction.
- **MCP originals:** large results retain opaque references for bounded paging
  without re-executing the tool. Scope includes the conversation, workspace and
  authority. TTL is 15 minutes; at most 64 entries / 32 MiB total / 8 MiB each.
  Server removal/configuration changes revoke retained results. Results remain
  untrusted data and memory-only.
- **Interruption journal:** bounded local metadata identifies interrupted runs
  and uncertain pending host tools. Desktop/mobile show a recovery warning. No
  automatic replay, credential persistence, or claim of exactly-once external
  side effects. Native session recovery keeps its existing fail-closed boundary.
- **Path validation:** inspect dangling symlinks/junctions with `lstat`, including
  new-file destinations. Root instruction reads verify file identity and use a
  file handle. This is not a substitute for OS isolation against a concurrent
  privileged filesystem attacker.
- **Publication hygiene:** scan new untracked source as well as tracked files,
  staged changes and reachable history. Run journal/runtime files are excluded.
- **Build/dependency maintenance:** Electron 43.7.7 and compatible dependency
  security patches; corrected the mobile lockfile's unavailable transitive
  version range against registry metadata. A separate short ASCII staging path
  avoids Windows CMake/Ninja path limits. Existing signing identity is retained.
  Desktop/mobile/package/server versions agree on 0.6.1 (Android version code 31).

## Existing capabilities retained and re-tested

Persistent per-ticket CLI sessions, bounded FIFO scheduling, owner-scoped
steering/cancellation, host-controlled computer-use observations, encrypted file
transfer, Discord authority/model ceilings, tuning profiles, opt-in local training
and pinned BFCL data/custom grading are existing foundations, not all new work.

## Verification and evidence boundaries

- Typecheck: agent, web, mobile.
- Full build/test suite, targeted adaptive/transport/recovery tests, computer-use
  fixtures, remote encryption/authority tests, coordination and tuning regressions.
- Browser UI: 1280x800, 820x650, 390x780 and 390x430. Model picker additionally
  verifies search/filter/toggle/provider switching. These are web viewports, **not**
  proof of real Android keyboard/IME behavior.
- Leak probe: 600 plugin calls, 80 WebSocket cycles and 20 stream start/stops;
  no leak detected in that bounded test, not a proof of indefinite leak-freedom.
- Official CLI updated to 0.159.3. Actual `gpt-6-sol` + Daybreak Blue inference and
  a tools-disabled defensive source review completed. Model-review hypotheses
  were not treated as confirmed vulnerabilities without a local regression.
- BFCL: pinned public data, custom grader, exact Sol 6, no model fallback,
  interleaved effort settings, separate development/holdout sets. No automatic
  production promotion. Detailed private reports live under ignored
  `release/validation/`; do not publish raw user conversations or model inputs.
- Dependency audits after these updates reported zero known vulnerabilities in
  both root and mobile lockfiles. This is a database check, not proof that the
  application has no vulnerabilities.

### Small Sol 6 experiment — no tuning promotion

The pinned BFCL subsets compare `medium` and `low` on the exact `gpt-6-sol`
model, using standard access (the Daybreak source review is a separate probe).
They use the local custom grader, not an official leaderboard submission.

| Set | Medium | Low | Medium p95 | Low p95 |
| --- | --- | --- | --- | --- |
| Development, 8 cases | 6/8 | 7/8 | 58.58 s | 14.40 s |
| Holdout, 12 cases | 11/12 | 11/12 | 20.71 s | 67.63 s |

The holdout did not justify changing all work to low effort: tail latency was
worse and tokens per successful case rose from about 7,083 to 7,380. No global
low-effort profile was promoted. The sample is too small to claim a general
accuracy or speed improvement. Measurements used the CLI transport evaluation
harness; they are not an end-to-end benchmark of the final installer.

## Not represented as completed

No third-party target penetration, published competition score, closed-model
weight fine-tuning, unrestricted downloaded skills, unmeasured automatic tuning
promotion, or full replacement of the native computer-use backend. Competition
problem sets without a verified public source/licence are not imported. Actual
Android device/IME validation and installation/deployment status must be reported
separately from source/build verification.
