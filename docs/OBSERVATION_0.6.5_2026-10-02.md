# 0.6.5 관측·오케스트레이션 회귀 검사

## 원인과 수정

이전 0.6.4 전이 검사 r6에서는 네 구성 모두 동일한 슬라이스를 잘못 읽었다.
계산기는 잘못 전사된 식을 정확하게 계산했기 때문에, 도구 실행과 동료의
동의만으로 원본 판독 오류를 잡지 못했다. 실패 기록은
[기존 보고서](EVIDENCE_VALUES_2026-10-02.md)에 그대로 남겨둔다.

이번에는 다른 언어 모델을 추가하지 않고 로컬 Tesseract OCR 관측을 원본과
나란히 제공했다. 직접 시험에서 핵심 슬라이스는 맞았지만 다른 문자에 오류도
있었다. 따라서 OCR은 항상 `verified:false`이며, 정답·명령·검증 결과가 아니다.
모델은 불일치한 부분의 원본을 대조해야 한다. 원본 코드를 자동 실행하거나
정답을 제품 프롬프트에 넣지 않았다.

## 실제 앱 비교: 기존 실패 사례 r7

정확한 `gpt-6-sol`, medium, Daybreak 끔, workspace 권한, 같은 질문과 두 원본을
사용했다. 인증된 설치 앱의 `chat.start`로 새 프로젝트/대화를 만들었고 직접
CLI 호출로 우회하지 않았다. 정답은 모델 작업공간 밖의 독립 CPython 참조와
대조했다. 회의는 검토자 2명과 최종 검증자 1명이며 계산량은 단일과 같지 않다.

| 구성 | 이전 r6 → 수정 후 r7 | r7 시간 | 입력 / 출력 / 캐시 입력 토큰 |
| --- | --- | ---: | --- |
| 단일 | 5/6 → 6/6 | 37.296초 | 42,949 / 678 / 26,624 |
| 온톨로지 | 5/6 → 6/6 | 45.168초 | 62,127 / 935 / 52,992 |
| 회의 | 5/6 → 6/6 | 58.937초 | 72,485 / 1,514 / 43,008 |
| 온톨로지+회의 | 5/6 → 6/6 | 90.469초 | 114,792 / 2,235 / 62,336 |

이는 **알려진 실패 사례의 회귀 수정**이다. 6개 항목은 두 코드 이미지에서 나온
세 질문씩이며, 독립된 6문제나 대회 공식 점수가 아니다. 같은 데이터 재검사라
일반화 증거로 삼지 않는다. 고정 순서·캐시·서비스 변동을 통제하지 않았으며,
모든 구성에서 정확도가 같고 회의형은 더 느렸다. 기본 단일 실행은 유지한다.
토큰은 누적 입력 보고값이며 캐시 입력을 별도로 더해 총량을 만들지 않는다.

## 새 사례 r8: 첫 OCR 구현의 한계도 보존

다른 문자·변수·연산 배치로 만든 새 이미지에서는 대문자/소문자 오류가
발생했다. 단일·회의·결합은 각각 5/6, 온톨로지는 6/6이었다. 첫 OCR의 잘못된
소문자 판독을 그대로 따른 것이 원인이며, 온톨로지가 글자를 교정한다고
결론내릴 수는 없다. 이 결과를 누락하거나 재시도로 대체하지 않는다.

| 구성 | r8 항목 | 시간 | 입력 / 출력 / 캐시 입력 토큰 |
| --- | ---: | ---: | --- |
| 단일 | 5/6 | 46.623초 | 68,313 / 900 / 54,016 |
| 온톨로지 | 6/6 | 49.482초 | 60,638 / 1,011 / 43,136 |
| 회의 | 5/6 | 84.735초 | 98,890 / 2,053 / 73,344 |
| 온톨로지+회의 | 5/6 | 64.841초 | 75,002 / 1,601 / 55,552 |

이를 바탕으로 신뢰도가 낮은 단어를 제한적으로 확대 재판독하고, 달라지는
문자를 숨기지 않고 두 가설로 제공하도록 수정했다. 확대 OCR도 추가 문자를
만드는 오류가 있어 어느 쪽도 정답으로 채택하지 않는다. 대신 **확대된 원본
픽셀**의 작은 모음과 좌표를 함께 제공해 직접 대조하게 한다. 전체 이미지를
계속 다시 여는 비용도 줄이려는 조치다. 이는 [Tesseract의 해상도·분할 모드 지침](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html)을
참고한 구현이며, 같은 엔진의 두 판독을 독립적인 정답 투표로 취급하지 않는다.

## 결정론적 소프트웨어 검사

### 확대 원본 재검사 r11

확대 원본 보조 이미지를 추가한 뒤 r8과 같은 원본을 다시 풀었다.
중간 r9는 사용자의 화면 조작 중단 후 평가도 취소했으며, 미완료 실행을
정답으로 세거나 r11로 덮어쓰지 않았다.

| 구성 | r11 항목 | 시간 | 입력 / 출력 / 캐시 입력 토큰 |
| --- | ---: | ---: | --- |
| 단일 | 5/6 | 74.086초 | 159,479 / 1,558 / 139,008 |
| 온톨로지 | 6/6 | 50.875초 | 85,369 / 1,010 / 64,000 |
| 회의 | 6/6 | 81.327초 | 146,107 / 2,414 / 116,992 |
| 온톨로지+회의 | 6/6 | 113.218초 | 249,360 / 2,811 / 200,704 |

회의와 결합에서는 알려진 대소문자 오류를 맞혔지만 **단일 실행의 오류는 남았다**.
비용과 시간이 늘었고 일부 구성만 개선된 한 번의 재검사다. 따라서 전체 정확도
개선, 회의형 우월성, 판독 문제 완전 해결을 주장하지 않는다. 기본 단일 실행을
회의형으로 변경하지 않았다. 인증된 설치 앱·정확한 Sol 6·medium 조건은 동일하다.

### 소프트웨어 회귀

- 온톨로지: 같은 상태 문자열의 무관한 사실 연결과, 한 개체의 타입 충돌이
  공유 분류 체계를 통해 다른 개체까지 오염시키는 문제를 재현/수정했다.
  시간은 기록 시점이며 사실의 유효 시점이나 진실 우선순위가 아니다.
- 회의: 여러 그룹 전체의 동시 호출 수, 대기 중 취소, 비협조적 시간 초과,
  한 그룹의 치명적 예산 실패가 다른 그룹도 중단시키는지 검사했다.
- OCR: 로컬 설치 자산의 해시, 실제 패키지 실행, 재사용, 취소, 크기 제한,
  동시 엔진 제한, 명시적 비활성화, fallible 메타데이터를 검사했다.
- 외부 공급자/기본 라우팅/권한/플러그인 설정은 보존하며, 평가용 메모리만
  생성 후 제거한다. 시험 중 사용자가 이어 쓴 대화는 정리 대상에서 제외한다.

## 단순 응답 지연 조사

설치 앱의 짧은 인사 요청 기록은 `gpt-6-astra`, 추론 `high`, Daybreak 끔이었다.
첫 답변까지 9.413초, 전체 10.341초였고 입력 11,086토큰, 출력 13토큰,
캐시 입력 0이 보고되었다. 도구 실행 0회·보조 에이전트 0개이며 온톨로지
검색은 0.074ms였다. 직전에는 20.768초 후 완료되지 않은 실행도 기록되어
있다. 따라서 이 요청의 지연을 병렬 회의나 온톨로지 검색 탓으로 볼 수 없다.

단일 모델은 한 번에 즉시 답한다는 의미가 아니다. 현 구현은 인사도 네이티브
CLI 작업 경로로 전달하므로 세션 준비, 도구 정의 등의 입력, 공급자 응답 대기
비용이 남는다. 다만 이 기록만으로 각각 몇 초인지 분해하거나 `high`가 원인이라고
입증할 수 없다. 모델의 비공개 추론을 읽지 않았으며, 보고된 reasoningTokens=0을
내부 추론이 전혀 없었다는 증거로 삼지 않는다.

조사 당시 `auto` 분류는 정형 인사를 direct로 처리했지만 한국어 초성 인사는 일반
요청으로 분류했다. 명시적 `high` 설정은 자동 분류보다 우선했다. 사용자 요구를
반영한 후속 수정에서는 초성 인사를 인식하고, 확실히 쉬운 요청에 지원되는 `low`를
전달한다. 저장된 작업용 선호·선택 모델·Daybreak·권한은 바꾸지 않으며, 일반/고난도
작업은 저장한 깊이를 유지한다. 튜닝 프로필이 전달 직전 이를 다시 높음으로
덮어쓰던 경로도 수정했다. 실행 상태와 route는 실제 강도를 표시한다.
경량화의 개선 여부는
같은 모델·같은 설정의 첫 응답/완료 시간, 세션 이어쓰기, 추가 지시와 취소 검증을
함께 통과해야 판단할 수 있다. [추론 설정의 일반적 시간·품질 상충](https://developers.openai.com/api/docs/guides/reasoning)은
참고 사항이며 해당 실행의 병목 측정값을 대신하지 않는다.

### 실제 설치 앱의 경량 대화 경로 비교

선택 모델 `gpt-6-astra`, 저장 강도 `high`, Daybreak 끔, full 권한, 같은 세 입력을
전후 각각 새 평가용 대화에 전달했다. 고정 순서이며 공급자 부하·캐시는 통제하지
않았다. 첫 수정은 강도만 낮췄고 인사가 오히려 15.539초 걸렸다. 이 실패도
남겨둔다. 따라서 강도만 바꾸면 지연이 해결된다고 결론내리지 않았다.

최종 수정은 확실히 쉬운 요청만 도구 없는 기존 CLI 텍스트 세션으로 보내며,
모델을 교체하거나 고정 문구로 답하지 않는다. 추가 작업은 같은 Mr.Robot 대화의
정식 기록을 이어받아 네이티브 작업 경로로 돌아간다.

| 입력 종류 | 변경 전 완료 / 첫 답변 | 경량 경로 완료 / 첫 답변 | 실제 강도 |
| --- | ---: | ---: | --- |
| 짧은 인사 | 5.512 / 4.337초 | 5.163 / 5.023초 | high → low |
| 단순 산술 | 5.624 / 4.811초 | 2.540 / 2.407초 | high → low |
| 앞 식과 답 재질문 | 4.742 / 3.691초 | 5.370 / 4.380초 | high → high |

첫 인사의 보고 입력 토큰은 11,214 → 3,445로 약 69% 줄었다. 산술 답과 후속
기억은 맞았고, 텍스트 세션 재사용과 작업 경로 복귀가 확인됐다. 도구 호출·보조
에이전트는 모두 0이며 저장 강도·모델·Daybreak·권한은 유지됐다. 인사의 첫 답변과
후속 재질문은 더 느렸으므로 **전반적 지연 개선이나 P95 개선은 아직 입증되지
않았다**. 확실히 입증된 것은 경량 경로·실제 강도 전달·입력량 감소·대화 연속성이다.

## 적용 기록

- PC 설치본 0.6.5의 `app.asar`가 최종 빌드와 동일한 SHA-256인지 대조했다:
  `b2325568598a7ace6ca6303d2748cb16b30a137a9513d11df41f4ec3db5823cb`.
- 최종 Windows 설치파일 SHA-256:
  `ede853589920eb444bcc6fbe0e245e0ff88b54e915e535877827b10ffb565d32`.
- 전체 회귀 통과 후, 후속 수정에 영향받는 추론/튜닝/네이티브 세션/AI 루프와
  타입 검사를 다시 통과했다. 단순 응답 중 추가 지시와 취소도 별도 검사했다.
- 화면 6종의 웹 UI 검사, 작은 디스플레이 창 배치와 모바일 타입/UI 계약을
  검사했다. 물리 Android 기기의 이번 APK/키보드 동작을 검증했다는 뜻은 아니다.
- 원문 일치·프로젝트 소유권을 확인한 평가 대화 17개만 보관했다. 빈 평가용
  프로젝트 등록 4개만 해제했고 파일은 삭제하지 않았다. 사용자가 이어 쓴
  이전 검사 대화는 그대로 보존했다.
- 공개 소스 및 도달 가능한 Git 이력의 민감정보 패턴 검사는 통과했다.
  알려진 패턴 검사는 모든 비밀정보·취약점의 부재를 증명하지 않는다.

## 연구를 적용한 범위

이미지의 작은 문자와 해상도 한계는 [OpenAI 이미지 가이드](https://developers.openai.com/api/docs/guides/images-vision)를,
독립적 로컬 OCR은 [Tesseract.js](https://github.com/naptha/tesseract.js)를 참고했다.
단계 분리와 유한한 병렬 실행은 [Anthropic의 multi-agent engineering](https://www.anthropic.com/engineering/multi-agent-research-system),
근거·시간 구분은 [Zep 연구](https://arxiv.org/html/2501.13956v1)를 참고했다.
이들 논문의 점수를 Mr.Robot 성능으로 인용하지 않는다. 전체 자동 테스트도
실제 세계의 모든 버그·취약점이 없다는 증거는 아니다.
